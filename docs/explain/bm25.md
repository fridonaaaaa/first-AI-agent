# bm25.py — explained

## What it does
Scores chunks against a query using BM25 (Best Match 25) — the standard
term-frequency ranking function used in search engines (Elasticsearch uses it by default).
It replaces SQL `ILIKE` or `ts_rank` with a proper relevance score computed in Python.

## The formula

```
IDF(t)     = log( (N - df + 0.5) / (df + 0.5) + 1 )

TF(t, d)   =          tf_norm * (k1 + 1)
               ─────────────────────────────────────────
               tf_norm + k1 * ( (1-b)/dl  +  b/avgdl )

score(q,d) = Σ  IDF(t) * TF(t, d)   for every query term t
```

**Variables:**

| Symbol | Meaning | Where stored |
|---|---|---|
| tf_norm | term count in chunk / total tokens | `bm25_postings.tf` |
| dl | token count of this chunk | `chunks.metadata['token_count']` |
| avgdl | average token count across all chunks | `bm25_corpus.avg_doc_len` |
| N | total indexed chunks | `bm25_corpus.total_docs` |
| df | chunks containing this term | `bm25_stats.df` |
| k1 | TF saturation (default 1.5) | config |
| b | length normalisation (default 0.75) | config |

## What each part does

**IDF (Inverse Document Frequency):** A term that appears in many documents is less
informative. If "the" appears in every chunk, its IDF ≈ 0. A rare term like "pgvector"
has high IDF, so it contributes more to the score.

**TF component:** A chunk that mentions "database" 5 times should rank higher than one
that mentions it once — but not 5× higher (diminishing returns). The k1 parameter
controls this saturation. At tf → ∞, the component saturates at (k1+1).

**Length normalisation:** A long chunk will naturally contain more terms. The b parameter
shrinks the score for longer chunks so a 10-word chunk mentioning "database" once is
not unfairly beaten by a 1000-word chunk that also mentions it once.

**Why stored tf is normalised (count/dl):**  
We substitute tf_raw = tf_norm × dl into the classical formula.
After simplification, dl cancels from the numerator and moves into the denominator
as `(1-b)/dl + b/avgdl`. This is mathematically identical to the original.

## Complexity

| Step | Cost |
|---|---|
| Tokenise query | O(|query|) |
| Fetch postings per term | O(df) per term — one SQL query per unique token |
| Score accumulation | O(total postings touched) |
| Sort | O(R log R) where R = number of matching chunks |

For a 3-term query with df ≈ 5,000 each: ~15,000 rows fetched, negligible sort.

## Edge cases

- **Term not in index:** `_get_term_df` returns 0 → term skipped, score contribution = 0.
- **tf_norm = 0 or dl = 0:** `bm25_score` returns 0.0 (guard in function).
- **All chunks contain the term (df = N):** IDF = log(1.2) ≈ 0.18 — small but positive.
- **Empty query (all stopwords):** `tokenise` returns [] → `search_index` returns [].
